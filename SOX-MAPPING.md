# SOX Control Mapping

**Purpose:** Map every architectural pattern in FinAgent OS to its corresponding SOX control type, COSO framework component, and explicit AI authority level.

**Scope:** This document is the source of truth for how FinAgent OS maintains control integrity in a SOX-regulated financial environment. It is referenced by the Agent Registry (`sox_control_ids`) and the agent workflows. A separate Risk Matrix document is planned.

**Author:** Rizwan Ahmed, ACCA · Velocyt Consulting
**Status:** v1.0, April 2026; statuses updated November 2026 for the phase 2 to 5 core

**Built, not live.** The statuses and implementation text below describe the phase 2 to 5 core in this repository: session identity, run start with a run token, decisions through one database function, the refusal journal, the admin audit, the error workflow and the sweep. None of it has been deployed. The hosted Supabase project and the n8n instance still run v1 until the cutover, and v1 has the gaps recorded in this document's git history (the November 2026 correction).

---

## Core Principle

> **AI is optional and non-authoritative. Policy decisions are deterministic. Every material financial decision is enforced by deterministic rules, not by model output. AI assists human judgment at the classification boundary; AI never has final authority over a control outcome.**

This principle is inherited from the ATLAS governance plane pattern and adapted to finance-specific controls. It answers the first question a SOX auditor asks about any AI-enabled workflow: *can an LLM hallucination cause a control to pass when it should have failed?* The answer in FinAgent OS is: no, because the control outcome is not produced by the LLM. The LLM produces advisory input; the policy engine produces the outcome.

**Key property:** no component calls an LLM, so FinAgent OS runs fully deterministically: every comparison, threshold, and policy rule fires without AI input. The four AI-advisory rows above are planned for v1.1. The runtime switch `FAO_AI_ASSIST_ENABLED` is not built yet: nothing reads it, and `agent_registry.ai_advisory_enabled` defaults to FALSE but is not checked at runtime. The ledger append function refuses any event that carries AI advisory fields. AI is designed to be additive to human judgment, not a replacement for deterministic controls.

**AI advisory is off.** The deterministic backbone (wallet-ledger comparison with fail-closed inputs, per-asset materiality and ratio evaluation, the policy outcome engine, a database rollup that routes any escalated asset to review, decisions bound to the signed-in approver, append-only evidence tables, correlation threading, registry checks at run start, and the MCP read surface) is built. **Of the 24 controls in this document, 11 are live in the phase 2 to 5 build, 7 are partial and 6 are planned.** "Live" here means built and passing its tests in this repository; it does not mean deployed (see the note at the top). Partial means part of the stated control is implemented and the rest is not; each row says which part. The 6 planned controls (`Planned (v1.1)`) cover AI-advisory features (FAO-REC-005, FAO-REC-009, FAO-GOV-010, FAO-GOV-011, FAO-GOV-012) and the rollback engine (FAO-GOV-005). The AI-advisory controls activate only after the AI switch is built and turned on, and that happens only after the AI threat model ships as its own ADR. This sequencing (deterministic spine first, AI advisory gated behind a flag and a published threat model) is deliberate. The deterministic ground truth has to be defensibly complete before AI is allowed near it.

## Control Type Definitions

For reference, because auditors and engineers use these terms differently.

| Type | Definition | Example in FinAgent OS |
|------|-----------|------------------------|
| **Preventive** | Stops an event from occurring. | HITL gate: a run that needs review is not committed until a signed-in approver, who is not the invoker, records a decision through `fao_hitl_decide`. |
| **Detective** | Identifies an event after it has occurred. | Shadow Ledger: each completed run records STARTED, one ASSET_RECONCILED event per asset, and COMMITTED in an append-only table. |
| **Monitoring** | Evaluates whether other controls are operating. | 5% randomized QA audit sampling agent outputs against their inputs (planned, v1.1). |
| **Corrective** | Reverses or mitigates the effect of an event. | Rollback Engine: staged changes can be reverted on failure or HITL rejection (planned, v1.1). |

COSO 2013 components referenced: (1) Control Environment, (2) Risk Assessment, (3) Control Activities, (4) Information & Communication, (5) Monitoring Activities.

Monitoring in COSO 2013 is a component (Monitoring Activities: ongoing and separate evaluations of whether the other controls work), not a transaction-level control type like preventive or detective. It is listed above because some rows use it; every row typed Monitoring is planned. Reconciliations and exception checks (FAO-REC-001, FAO-REC-003, FAO-REC-007) are detective control activities, so they map to Control Activities.

## Architectural Pattern → Control Mapping

Every pattern in FinAgent OS has a Control ID in the format `FAO-XXX-NNN` where `XXX` is the governance area:

- `FAO-GOV`: Governance layer (platform-wide controls)
- `FAO-REC`: Reserve Reconciliation Agent
- `FAO-CLS`: Close Orchestrator (stub)
- `FAO-VAR`: Variance Analyzer (stub)
- `FAO-TRE`: Treasury Monitor (stub)

### Platform Governance Controls (FAO-GOV)

| Control ID | Pattern | Type | COSO | AI Authority | Status | Implementation |
|------------|---------|------|------|--------------|--------|----------------|
| **FAO-GOV-001** | Shadow Ledger immutable audit trail | Detective | Information & Communication | None | Partial | Postgres tables in Supabase. Shadow Ledger rows are appended only by the FinAgent database functions: the Writer's batch call `fao_ledger_append_batch` (STARTED, ASSET_RECONCILED and FAILED; all or none, naming every bad item) and the functions that write the run, HITL, notification, commit and correction events. Timestamps are set by the database, and run context (execution id, agent, risk tier, invoker) is set or checked by it. No application role holds INSERT, UPDATE, DELETE or TRUNCATE on any FinAgent table. Row triggers refuse UPDATE and DELETE on the ledger and the other evidence tables for every role, and a statement trigger refuses TRUNCATE on every FinAgent table, the owner included unless the owner disables it. A completed run writes STARTED, one ASSET_RECONCILED record per asset and COMMITTED; a run that needs review also writes HITL_REQUESTED, and the decision writes HITL_RESOLVED and COMMITTED in the same transaction. A run whose chain is incomplete gets COMMIT_BLOCKED instead of COMMITTED. Failures are recorded: the flagship, the notifier and the sweeper name an error workflow that calls `fao_run_fail`, which writes a FAILED event on the flagship run or, when the failure is not tied to an unfinished flagship run, one row in the append-only `workflow_failures` table; the five-minute sweep fails runs left RUNNING past the agent's `sla_max_execution_seconds`, which the database refuses to set below 900; the flagship's n8n `executionTimeout` of 600 seconds stops a slow execution before that. The Writer has no error workflow of its own: a Writer failure fails the flagship execution, which is recorded. Refusals returned by the FinAgent functions are written to the append-only `fao_refusal_journal` in the same transaction, with a per-caller cap each minute (past the cap one marker row; refusals continue). Changes to configuration tables need a change reason and write before and after images to the append-only `fao_admin_audit`. Corrections are new CORRECTION rows written by the admin-only `fao_ledger_correct`; the original row is never changed. Not covered: refused direct table writes are not journaled (planned), and requests that PostgREST refuses before any function runs appear only in platform logs. The database owner (`postgres`, `supabase_admin`) and holders of platform admin or secret keys are a separate trust class outside the control: they can disable triggers or change rows. That is by design, because a database cannot protect evidence from its own owner; an independent evidence store is planned and not built. |
| **FAO-GOV-002** | Agent Registry (formalized control population) | Preventive | Control Activities | None | Live | Postgres table (`agent_registry`) in Supabase with foreign keys to `process_owners`. The registry gates every run: `fao_run_start` refuses an unknown agent, refuses an agent that is not ACTIVE (and commits a RUN_REFUSED ledger row with the refusal), requires the caller to hold the invoker role for that agent, and enforces the agent's `max_runs_per_hour` per invoker (a replay of an expired run's idempotency key counts toward it). It also refuses an `sla_max_execution_seconds` below 900. Status is checked again later: a claim for an agent that is no longer ACTIVE is refused and the run expires, and at finalize or on an approval the run gets COMMIT_BLOCKED instead of COMMITTED and ends FAILED. The HITL request timeout comes from the registry SLA. A change to a registry row needs a change reason in the same transaction and writes before and after images to `fao_admin_audit`; `updated_at` is set by a trigger. Admins change status, the AI flag and the run limit through `fao_admin_set_agent` with a reason. |
| **FAO-GOV-003** | Risk-Tier Classification (GREEN/AMBER/RED/BLOCKED) | Preventive | Risk Assessment | None | Live | Every agent has a `risk_tier` on `agent_registry` (Supabase). CHECK constraints forbid BLOCKED as the tier of an agent, a run or a new HITL request, since BLOCKED is reserved for policy outcomes. The tier is copied from the registry into the run record at run start and from the run into the HITL request; no caller supplies it, and a Writer event whose tier differs from the run's is refused. The agent's `approval_threshold` (two for RED) is recorded on each request as its configured approval count; one approval is enforced, because dual approval is excluded (see [ADR-0001](docs/adr/0001-dual-approval-not-yet-enforced.md)). |
| **FAO-GOV-004** | HITL Gateway with segregation-of-duties enforcement | Preventive | Control Activities | None | Partial | Decisions are recorded only by `fao_hitl_decide`, called with the approver's own Supabase Auth session; the approver is taken from `auth.uid()`, never from a payload, and the invoker was recorded the same way at run start. No application role can write `hitl_queue` directly. A row trigger that applies to every role, the owner included, enforces the rules: the approver is the signed-in user, is not the invoker, and holds the approver role for the agent; no decision at or after the deadline; decided requests cannot change and no request can be deleted. A decision (approve or reject) by the run's invoker is refused with SOD_SELF_APPROVAL (403) and written to the refusal journal; nothing is written to the Shadow Ledger. An approval for a run whose invoker is no longer an active owner holding the invoker role is recorded but not committed (INVOKER_NOT_ACTIVE). The decision and its ledger events commit in one transaction. The old `fao_hitl_resolve` always raises, and the n8n approval pages are retired. Limits: one approver per request until dual approval (ADR-0001, excluded); no second factor yet (TOTP is planned), so a stored password is enough to approve for any user with the approver role; the database owner and holders of platform admin keys are outside the control (see FAO-GOV-001); and in the public demo one person holds every demo identity, so the control binds actions to identities but cannot prove they are different people. |
| **FAO-GOV-005** | Rollback Engine (Break / Commit / Rollback) | Corrective | Control Activities | None | Planned (v1.1) | Staging area pattern. Agents will write intended changes to staging; commit only on successful HITL approval; revert staged changes on failure or rejection. Today a rejected request is logged with ROLLED_BACK as the `execution_status` of the run's COMMITTED event, but nothing is staged or reverted; CORRECTION rows (FAO-GOV-001) correct the record, they do not roll anything back. The staging-area workflow ships in v1.1. |
| **FAO-GOV-006** | Database-First Vault Capture | Preventive | Control Activities | None | Partial | The STARTED record is written to Postgres (Supabase) through the Writer before reconciliation runs, and the database adds the invoker, the invocation channel, the reason and the n8n execution id from the run record. A STARTED whose inputs carry any of those four keys (at any depth, in any normalised spelling) is refused and nothing is written (owner decision 2026-11-08); the flagship sends none of them, and `check-exports` rule `started_db_keys` holds that. Each ASSET_RECONCILED record stores that asset's wallet and ledger balances. No LLM calls are made. Full upfront raw capture is not achieved: the raw wallet and ledger input sets travel with the STARTED item but the Writer's Validate Batch strips them, so a failure before the per-asset writes leaves the inputs unrecorded (the failure itself is recorded, see FAO-GOV-001). |
| **FAO-GOV-007** | Webhook-Gated State Progression | Preventive | Control Activities | None | Live | State transitions wait for authenticated confirmations. A run starts only when the n8n invoke webhook, which requires a header key, receives a single-use run token that `fao_run_start` issued to a signed-in invoker; `fao_run_claim` consumes the token (stored only as a hash, valid for 10 minutes) and refuses a forged, expired or reused one. A HITL request leaves PENDING only through `fao_hitl_decide` (FAO-GOV-004), which writes HITL_RESOLVED and COMMITTED in the same transaction. Approvers decide on a static approval page (`approval-app/`), signed in with their own account. Slack notices only link to the page: every attempt is recorded, failed sends are retried by the five-minute sweep up to `notify_max_attempts`, and an overdue request expires and escalates once (HITL_EXPIRED is the expiry record, which the escalation and, on an incomplete audit chain, COMMIT_BLOCKED can follow; the sweep never writes COMMITTED for it). A request with no notice sent within the notice window is escalated once and no longer re-sent; the owner accepted that sweep rule as built on 2026-11-08. Payment webhooks and scheduled cron confirmations are not part of the build. The page's logic is unit-tested; its sign-in and decision flow is checked by hand once per release (there is no automated browser test), and that check has not yet been recorded for this build. |
| **FAO-GOV-008** | Correlation ID threading | Detective | Information & Communication | None | Live | `fao_run_start` creates the run record (`run_invocations`) and the database generates its `correlation_id` and `execution_id`. Every Shadow Ledger entry and HITL request for the run carries the same correlation id, and the run record holds the invoker, reason, state and n8n execution id. A trigger enforces the run states (REQUESTED, RUNNING, AWAITING_HITL, then COMMITTED, FAILED or EXPIRED; a finished run never changes). Every client RPC takes one JSON body that the database decodes and validates; an unknown, missing or repeated key, or a value that is not a string, is refused with INVALID_INPUT and journaled. The view `fao_run_summary` gives one row per run. Enables end-to-end audit trace from trigger to outcome. |
| **FAO-GOV-009** | Policy Outcome vocabulary (ALLOW / ALLOW_WITH_OBLIGATIONS / REQUIRE_HUMAN / DENY / BLOCKED) | Preventive | Control Activities | None | Live | Every completed run records one rollup policy outcome on its COMMITTED row, and each asset gets one per-asset outcome. Outcomes are deterministic: computed by rules, not generated by an LLM. The rollup is computed once, in the database (`fao_private.run_rollup`), from the stored asset rows. A run that fails before finalize records a FAILED event and no rollup outcome (see FAO-GOV-001). |
| **FAO-GOV-010** | 5% Randomized QA Audit sampling | Monitoring | Monitoring Activities | None | Planned (v1.1) | Sampling job will select 5% of agent executions per week. Process Owner reviews each sample: input, AI advisory (if present), policy outcome, match to expected. Deviations logged and drive rubric refinements. |
| **FAO-GOV-011** | Fractional API Cost Tracking | Monitoring | Monitoring Activities | None | Planned (v1.1) | Every AI advisory call will log prompt tokens, completion tokens, and USD cost (6-decimal precision) to Shadow Ledger. Schema columns (`ai_prompt`, `ai_output`, `ai_confidence`, `fractional_cost_usd`) exist and are NULL across all v1 rows; while AI advisory is off, the ledger append function refuses any event that sets them. Population begins when `FAO_AI_ASSIST_ENABLED=true` ships. |
| **FAO-GOV-012** | Closed-Loop Rubric Refinement with HITL Gate | Monitoring + Segregation of Duties | Monitoring Activities | Advisory | Planned (v1.1) | Weekly audit job will aggregate outcomes, flag anomalies where AI advisory diverged from human decision, propose rubric changes. All changes require human approval before deployment. AI proposes; human disposes. |
| **FAO-GOV-013** | Process Owner Named on Every Agent | Preventive | Control Environment | None | Live | Agent Registry schema requires a foreign key to `process_owners`: an identity record tied to a Supabase Auth user, not a free-text string. Every registry row, and so every agent that writes to the Shadow Ledger, has a named Process Owner. Owners are deactivated, not deleted: `fao_admin_set_owner_active` sets `active`, and a referenced owner cannot be deleted. Application roles (invoker, approver, admin, reader) are rows in `fao_user_roles`, revoked rather than deleted; an inactive owner's invoker, approver and admin roles stop counting. This addresses the named-Process-Owner part of the governance requirement *"No build goes to production without a named Process Owner, documented data flows, access controls, and audit logging confirmed."*; access control and audit logging are now enforced in the database, with the limits stated in FAO-GOV-001 and FAO-GOV-004. |
| **FAO-GOV-014** | AI Disabled by Default | Preventive | Control Environment | None | Partial | AI advisory is off: no workflow calls an LLM, `agent_registry.ai_advisory_enabled` defaults to FALSE, and the ledger append function refuses events that carry AI advisory fields. The runtime switch is not built: nothing reads `FAO_AI_ASSIST_ENABLED` or checks `ai_advisory_enabled` at runtime. Changing the flag is a logged configuration change: it needs a change reason and writes before and after images to `fao_admin_audit` (through `fao_admin_set_agent`, or owner SQL with a reason). |
| **FAO-GOV-015** | MCP Tool Surface (Read + Bounded Invoke; No Governance Mutation) | Preventive | Control Activities | None | Live | Python FastMCP server ([`mcp/server.py`](mcp/server.py)) exposing 6 read tools and 1 bounded invoke tool. There is deliberately no `approve_hitl`, no `update_threshold`, no `register_agent`. The database enforces the same asymmetry: the server reads as a dedicated Supabase Auth user that holds only the global `reader` role, and refuses to start if a service or secret key is in its environment or if the reader holds any other role. The database refuses the reader's writes and workflow calls, and the service-role key has no privilege on any FinAgent object. The invoke tool signs in as a named human invoker and calls `fao_run_start` with that person's session, so the registry, role and rate-limit checks apply; a retry with the same idempotency key replays the same run. The grant allow-list is asserted when the migrations run, and the five-minute sweep reports any drift from it. Read results move text written by users under an `untrusted_text` field. History: the self-audit of Apr 25, 2026 (via Claude Opus, tool discovery only) and the screenshots in [`docs/evidence/mcp/`](docs/evidence/mcp/) cover the v1 server, which held a service key, and mention database layers since replaced; they are kept as a record, not as evidence for this build. See [`mcp/README.md`](mcp/README.md) and the [self-audit transcript](https://claude.ai/share/5f0eb294-e658-42b5-a876-8164a0049960). |

### Reserve Reconciliation Agent Controls (FAO-REC)

| Control ID | Pattern | Type | COSO | AI Authority | Status | Implementation |
|------------|---------|------|------|--------------|--------|----------------|
| **FAO-REC-001** | Wallet-Ledger Balance Comparison | Detective | Control Activities | None | Live | Per-asset deterministic arithmetic: `discrepancy = wallet_balance - ledger_liability`. No AI. Inputs fail closed: an asset present on one side only, or a balance that is not a finite number, is BLOCKED and routed to human review instead of compared. |
| **FAO-REC-002** | Per-Asset Materiality Threshold Evaluation | Preventive | Control Activities | None | Live | For stablecoin assets: if ledger − wallet > materiality_usd (a shortfall) and the ratio is neither below the floor nor above the band → REQUIRE_HUMAN STANDARD (IN_BAND_USD_MATERIAL). A surplus inside the band is governed by the band upper alone and ALLOWs (owner decision 2026-11-08). With the seeded floor equal to the band lower (1.0000), every stablecoin shortfall is caught first by the floor rule as BELOW_FLOOR CRITICAL, so this rule fires only under a threshold whose floor is below 1.00; it is tested offline with a threshold override, not end to end. Deterministic rule. An asset with no usable threshold is BLOCKED and routed to review; a run that finds no threshold rows at all stops with an error, which is recorded. Threshold changes need a reason and are audited (`fao_admin_set_threshold`). Limits: non-stablecoin USD materiality is deferred pending price oracle integration; the FAO-REC-004 ratio check provides primary coverage (see README Limitations). The seeded USDC and USDT band is [1.0000, 1.0500]: the owner decided on 2026-11-07 that stablecoin reserves are held near 105%, so a ratio up to 1.05 is in band and only a ratio above 1.05 escalates as ABOVE_BAND_UPPER (IC-38). The live table holds 1.0050 until the cutover runbook applies 1.05 through `fao_admin_set_threshold` with a change reason. |
| **FAO-REC-003** | Reserve Ratio Computation | Detective | Control Activities | None | Partial | `reserve_ratio = wallet_balance / ledger_liability` per asset, stored on each ASSET_RECONCILED row. No AI. No aggregate ratio across assets is computed: the database rollup never sums units across assets and has no ratio field (a pgTAP test checks this). An aggregate needs a defined scope, a common valuation basis and a floor before it can be built; it is planned. |
| **FAO-REC-004** | Reserve Ratio Threshold Check | Preventive | Control Activities | None | Partial | If an asset's `reserve_ratio` is below its configured `ratio_floor` (1.00 for every seeded asset), that asset's policy outcome = REQUIRE_HUMAN CRITICAL and the run goes to human review. Deterministic rule; no AI input. The aggregate floor check is not built: no aggregate floor is configured or evaluated (see FAO-REC-003). |
| **FAO-REC-005** | AI Discrepancy Advisory Classification | Detective | Information & Communication | Advisory | Planned (v1.1) | When `FAO_AI_ASSIST_ENABLED=true`, LLM produces advisory classification (CLEAN / BENIGN_TIMING / ANOMALY / MATERIAL) with reasoning. Classification is input to FAO-REC-006, never the output. The switch is not built and AI advisory is off. `ai_prompt`, `ai_output`, `ai_confidence` columns are NULL across all v1 rows, and the ledger append function refuses events that set them; the deterministic policy engine runs without AI input. |
| **FAO-REC-006** | Policy Outcome Engine | Preventive | Control Activities | None | Live | Deterministic function: given materiality check (FAO-REC-002), ratio check (FAO-REC-004), and (when enabled) AI advisory (FAO-REC-005), compute one of: ALLOW (auto-log only), ALLOW_WITH_OBLIGATIONS (logged with a weekly-review obligation; the review itself is not automated), REQUIRE_HUMAN (HITL gate), DENY (rejected with reason), BLOCKED (never auto-proceeds; routed to review). Per-asset outcomes are computed in the flagship workflow; the run outcome is the worst asset's, computed in the database. Any asset that is REQUIRE_HUMAN, DENY or BLOCKED routes the whole run to one human review request, with review sub-tier CRITICAL when any asset is DENY, BLOCKED or CRITICAL. Missing, one-sided or non-finite balances and assets with no threshold are BLOCKED. Limits: no current rule produces DENY; the database checks the shape, completeness and fail-closed inputs of each asset row and the audit chain, not the policy result itself, which the workflow computes. |
| **FAO-REC-007** | Negative-Balance Anomaly Detection | Detective | Control Activities | None | Live | Per Kraken's own 2014 PoR reference implementation (`krakendb`), "large negative values" at leaf nodes require investigation. Agent flags any negative ledger liability as REQUIRE_HUMAN CRITICAL. Deterministic rule. |
| **FAO-REC-008** | Audit Evidence Package Generation | Detective | Information & Communication | None | Partial | Each run writes correlated, timestamped JSON records to the Shadow Ledger: STARTED, one ASSET_RECONCILED record per asset (balances, ratio, threshold, policy outcome and rationale), and COMMITTED with the per-asset summary, written in the same transaction as the rollup; when the chain is incomplete the run gets COMMIT_BLOCKED, naming the missing, duplicate or unexpected assets, instead. The view `fao_run_summary` gives one row per run with its state, request, decision and latest committed outcome. No step assembles these into one self-contained evidence package; that is planned. The records are retrieved by `correlation_id`. AI advisory fields are NULL. |
| **FAO-REC-009** | Human Approval Brief (AI Advisory) | Monitoring | Monitoring Activities | Advisory | Planned (v1.1) | When policy outcome = REQUIRE_HUMAN and `FAO_AI_ASSIST_ENABLED=true`, LLM generates a plain-English brief summarizing the discrepancy, the AI advisory classification, and the reasons for escalation. Brief is attached to the HITL request via `hitl_queue.ai_human_brief`. Does not alter policy outcome or substitute for human judgment. The column is not set by any code today; the deterministic `policy_rationale` is shown to approvers on the approval page as the authoritative source. |

## Governance Requirements Crosswalk

The governance requirements typical of an AI-agent platform in a SOX-regulated financial environment fall into seven dimensions. Each maps to one or more controls above.

| Governance Requirement | FinAgent OS Controls |
|-----------------------|---------------------|
| Data classification | FAO-GOV-002 (Agent Registry declares data sources per agent, production targets named: Fireblocks, NetSuite, Kyriba) |
| Auditability | FAO-GOV-001 (Shadow Ledger, refusal journal, admin audit), FAO-GOV-008 (correlation ID threading), FAO-REC-008 (audit evidence records; the package is planned) |
| Human-in-the-loop checkpoints | FAO-GOV-004 (HITL Gateway), FAO-REC-006 (policy outcome engine routing REQUIRE_HUMAN, DENY and BLOCKED to review) |
| Failure detection | FAO-GOV-001 (the error workflow records a FAILED event or a `workflow_failures` row; the sweep fails stale runs; an incomplete audit chain gets COMMIT_BLOCKED), FAO-GOV-005 (Rollback Engine triggered on failure, planned v1.1) |
| Rollback mechanisms | FAO-GOV-005 (Break/Commit/Rollback staged changes) |
| Regulatory compliance | Every control above maps to a SOX control type and COSO component |
| Audit-ready design documentation | This document, the root `README.md`, and the decision records in [`docs/adr/`](docs/adr/). `docs/ARCHITECTURE.md` and `docs/AGENT-GUIDE.md` are planned. |

**Risk-tier-before-build requirement.** A common requirement in this domain: *"Classify all automation builds by risk tier before work begins. No build goes to production without a named Process Owner, documented data flows, access controls, and audit logging confirmed."* This is addressed in part by FAO-GOV-002 + FAO-GOV-003 + FAO-GOV-013 + FAO-GOV-001. The registry schema requires a named Process Owner and a risk tier for every agent, and a HITL request cannot be created for an agent without a registry row and SLA. A run cannot start unless the registry row is ACTIVE and the invoker holds the invoker role; the tier comes from the registry, and status is checked again at claim, finalize and approval. This build has not gone to production yet (see the note at the top).

## Prior Art and Acknowledgements

FinAgent OS does not exist in a vacuum. The governance-first design is informed by publicly available prior art in the agentic AI and financial controls space:

- **[ATLAS (`quantumlayer-atlas/atlas`)](https://github.com/quantumlayer-atlas/atlas)**: the first principle that AI should be optional and non-authoritative in policy decisions. The "Where is the AI?" table format at the top of this document is adapted from their approach.
- **[Kraken's own `krakendb` (Payward, 2014)](https://github.com/krakenfx/krakendb)**: the PoR hash scheme reference, the canonical operational concern about negative-balance leaves, and the principle that external verification is necessary for trust.
- **[Kraken's `kraken-cli`](https://github.com/krakenfx/kraken-cli)**: the *AI-native* framing applied to a Kraken-shipped trading system, the convention of dedicated agent-facing root documentation alongside the human README, the structured-JSON output discipline at workflow boundaries, and the MCP-server-as-first-class-component design pattern. The discovery of OpenClaw as prior art happened through their documentation.
- **[Dewale-A's `Agentic-Accounting-Close`](https://github.com/Dewale-A/Agentic-Accounting-Close)**: the concrete dollar-threshold materiality gate pattern and the approach of enforcing segregation of duties at the API boundary rather than as documentation.
- **[OpenClaw Airlock (`tushar5623/OpenClaw_Airlock`)](https://github.com/tushar5623/OpenClaw_Airlock)**: the GREEN/AMBER/RED/BLOCKED risk tier vocabulary and the per-action decision matrix pattern.
- **COSO 2013 Internal Control: Integrated Framework**: the five-component structure every control maps to.

Adopted prior-art patterns are cited above. FinAgent OS extends them by applying governance-first architecture to crypto-native financial infrastructure. Decision records are in [`docs/adr/`](docs/adr/).

## Change Control

This document is versioned in git. **In v1 and through phases 2 to 5**, changes are direct commits by the single author; the phase 2 to 5 commits were co-written with an AI coding assistant (recorded in `Co-Authored-By` lines). The history has no pull requests and no PR review record.
